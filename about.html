The Goal

What I Set Out to Build

I built this to answer one question a recruiter or hiring manager should be able to ask: can this person actually do the job? Not in the abstract — but concretely. Given raw customer data, can they identify the opportunity, size the robots correctly, model the ROI, and build a presentation that a non-technical VP would understand?

This isn't a slide deck about what robotics can do. It's an end-to-end demonstration of the analytical process an SE runs in the first 4-6 weeks of a customer engagement — from the initial data request all the way through to the phased deployment proposal. Every calculation is visible and explainable. Every recommendation ties back to a number.

The secondary goal was to build something reusable. These calculators aren't one-offs for a synthetic example — they're structured so an SE could drop in a real customer's data and run the same analysis in an afternoon rather than from scratch.

Tools Used

How It Was Built

The stack was deliberately minimal — everything runs in a browser or on the command line with no proprietary systems required:

Python + pandas
All core analysis — transaction processing, ABC tiering, slotting drift detection, fleet sizing math, and data generation for synthetic datasets
Claude (Anthropic AI)
Development acceleration — writing Python scripts, HTML calculators, the Word report generator, and SVG diagrams. All analytical decisions, framing, and validation were mine.
HTML / CSS / JavaScript
All calculator and presentation pages — no frameworks, no build step. Runs as a static site from any folder or GitHub Pages.
Node.js + docx
Generated the full 9-section Word report programmatically — tables, formatted sections, callouts, and CapEx scenario comparisons
GitHub + GitHub Pages
Version control and free static hosting — anyone with the URL can access the full portfolio and run every calculator
SVG (hand-written)
Warehouse facility and pick face layout diagrams — precise, scalable, and renderable in any browser without external dependencies
On using AI for development: I used Claude throughout this build as a development accelerator — it wrote the bulk of the HTML, Python, and Node.js code. The analytical structure, methodology decisions, number validation, and narrative framing were all mine. I treated it like a very fast junior developer: give it a clear spec, review what it produces, and push back when the math or framing is wrong. The final output is only as good as the person directing it.

The Process

How I Followed an SE Engagement Workflow

I structured the build to mirror the order of work an SE actually does — not skipping ahead to the robot recommendation before the baseline is understood:

1
Define the data request. What would I actually ask a customer for? OB transactions, IB receipts, inventory snapshot, SKU master. Minimum viable dataset that allows a real ROI conversation.
2
Establish the baseline before any robot talk. Capacity utilization, current UPH, zone distribution, slotting health. You can't claim a 25% UPH gain if you don't know what 100% looks like today.
3
Slotting review before robot sizing. 1,618 SKUs were misplaced — that's 32% of the catalog in sub-optimal zones. You cannot reliably size a P2G robot fleet into a broken slot structure.
4
Score categories for robot fit — with criteria, not intuition. H&B scored 93% for Array. Apparel scored 85% for Origin. The scores come from observable criteria with explicit weights — an SE can defend them in front of a customer operations VP.
5
Size the fleet from throughput demand, not catalog size. 4 Array robots × 176 picks/hr × 22 hrs = 15,488 picks/day — exactly covers H&B daily demand. Derived by working backward from the data, not guessing.
6
Phase the proposal to de-risk for the customer. Start with Origin in Apparel (zero CapEx, proven ROI within weeks) before asking the customer to commit to racking changes and a new robot type in H&B.
7
Build a customer-facing deliverable that hides the complexity. The customer presentation shows five clean slides. The full 9-section report and these calculators are the work behind it — not what gets put in front of the VP of Operations.

Domain Knowledge

Where the Locus Knowledge Came From

I didn't come into this with an SE background at Locus. Here's exactly where the domain knowledge in this analysis comes from:

Locus-Specific

  • Public product materials and press releases for Origin, Array, NeuraGrasp, and LocusONE
  • Published UPH improvement benchmarks (25-35% for P2G) and R2G pick rate ranges (150-300 picks/hr)
  • RaaS pricing model structure — confirmed no CapEx for robots, monthly subscription
  • $1,500/robot/month for Origin (confirmed); $4,000/robot/month for Array (planning assumption, needs account team confirmation)

Warehouse Operations

  • ABC velocity tiering methodology — industry standard, widely documented
  • Three-bucket time model: active pick / travel / overhead (42% / 26% / 32% split)
  • UPH benchmarks for manual e-comm fulfillment (65-85 range)
  • Walk distance as a measurable, calculable waste metric
  • IB/OB conflict patterns in two-shift operations
  • Min/max replenishment logic and reserve-to-pick-face flow
The honest caveat: Several inputs in this analysis are estimated rather than measured. Zone distances from Pack/Ship (A=50 ft through E=525 ft) are approximations from the facility layout, not tape-measured. The Array pick rate of 176 picks/hr was derived by working backward from H&B daily demand — it falls within the published R2G spec range but is not based on a Locus-provided figure for this specific item mix. A real engagement would validate both of these with a site survey before quoting a number to the customer.

Strengths

What This Approach Gets Right

Analytical

  • Every recommendation is traceable to a number in the underlying data
  • Methodology is explicit — an SE can explain any figure to a customer without referring back to a black box
  • Slotting-first sequencing prevents fleet sizing mistakes
  • Three-bucket time model is more defensible than a single "percent improvement" claim
  • Three CapEx scenarios (not one) because the real answer requires a site survey

Structural

  • Reusable — swap in a real customer's data files and the calculators regenerate
  • Phased deployment de-risks for the customer — Phase 1 has zero CapEx and validates ROI before Phase 2 commitment
  • Two expansion paths give the customer options without making Array feel like a forced upsell
  • Customer presentation is separately designed for a non-technical audience — the analysis stays in the SE's toolkit

Honest Gaps

What Needs Validation in a Real Engagement

These are the places where this analysis makes assumptions that a real SE would validate on-site or with the Locus account team before presenting a number to a customer:

Zone distances are estimated. The 50/150/275/400/525 ft zone distances from Pack/Ship were read off the facility layout, not measured. Walk distance and UPH calculations are sensitive to this — a 10% error in distance propagates to the labor savings number.
Array pricing needs account team confirmation. $4,000/robot/month is a planning assumption, explicitly flagged throughout. The real figure depends on fleet size, contract term, and customer-specific negotiation.
Array pick rate is back-derived, not published. 176 picks/hr/robot was calculated from H&B daily demand ÷ (4 robots × 22 hrs). It sits in the middle of the 150-300 picks/hr R2G benchmark range, which makes it defensible — but a Locus SE would validate against NeuraGrasp throughput data for this specific item mix.
NeuraGrasp graspability is category-level, not SKU-level. H&B scored 4/5 for graspability based on general packaging profile. A real engagement would pull unit dimensions and weights from the SKU master and run item-level confidence checks — some tubes, pouches, and flexible packaging in H&B would score lower.
Slotting calculator is human-optimized. The current slotting tool uses ergonomic tier (prime, secondary, floor) as a scoring factor. Array removes the ergonomic tier entirely — robot arm reach is the constraint, not human back angle. In an Array scenario, the slotting logic would be recalculated against robot-specific constraints.

Where This Goes

What I'd Build Next as an SE at Locus

These calculators are a working foundation. Here's the roadmap I'd pursue to turn them into a standard SE team asset:

Robot Mode Toggle — Slotting Calculator

Switch the slotting optimizer from "human mode" to "Array mode" and re-rank zones by robot arm reach, not ergonomic tier. Show the SE exactly how the slotting recommendation changes when Array enters the picture.

SKU-Level NeuraGrasp Scoring

Pull unit dimensions and weights from the SKU master and score NeuraGrasp graspability at the individual item level — not category-level. Surface exceptions within a "good" category before they become surprises at go-live.

WMS Data Connector

Replace the CSV file drop with a live WMS export connection. The SE runs a data pull during the site visit and the calculators auto-populate — instead of a 2-3 day turnaround on analysis, it's same-day.

Vertical-Specific Benchmarks

Preset configurations for common Locus verticals — 3PL, retail replenishment, grocery, pharmaceutical. Each vertical has different UPH norms, ergonomic profiles, and IB patterns. Pre-loading these saves the SE from re-deriving benchmarks for every engagement.

Multi-Site Comparison

Enterprise customers often have 5-20 DCs. A multi-site scoring tool would let the SE rank DCs by robotics opportunity — which sites have the highest ROI per dollar, and in what order should they be sequenced for rollout.

SE Onboarding Version

A guided walkthrough version of the calculators for new Locus SEs — explains why each input matters, shows the analysis methodology step by step, and calibrates the SE's judgment against known good examples before they run their first real engagement.

The bigger picture: The goal is to reduce the time from "customer shares data" to "SE has a defensible proposal" from two weeks to two days. Every hour the analysis takes is an hour the customer is not moving forward. These calculators are a step toward that — but the version that runs in two days requires tighter data connections, more automation in the analysis layer, and institutional calibration of the benchmarks against real Locus deployments.
